# A6 design contract — the site (v3)

Static site under `site/`, published by `.github/workflows/pages.yml` to GitHub Pages (source: GitHub Actions, no branch juggling) at https://oliver139-chinesemole.github.io/berkeley-waitlist-odds/. No backend, no build step, no framework, no external scripts or fonts (GoatCounter, when Oliver adds it, is the one planned exception). Several pages share one stylesheet (`site/assets/site.css`) and one script (`site/assets/site.js`, exposing `BWO`); each page carries its own short inline script. Data is the JSON `analysis/export.py` writes to `site/data/` (docs/DESIGN_A5.md section 4), committed to `main` by `.github/workflows/analysis.yml` every Sunday at 15:23 UTC (or by dispatch), which also copies the report and figures to `reports/`. Until the Spring 2027 collection has clearings, the JSON comes from the Fall 2026 backfill (`make backfill-analysis`, `make site-data`; docs/DESIGN_A5.md section 9) and `meta.data_source` is `berkeleytime_history`. The plan behind v3, with priorities and the decisions taken, is docs/dev/SITE_V3_PLAN.md.

## Rules every page keeps

- The pages read precomputed JSON and compute no statistic: a curve is read at a horizon (`BWO.readCurve`, the last grid point at or before the horizon; past the reach the last point stands, so the share by then is at least that, which every page says as "at least" and leaves out where the share prints as 100%). Nothing simulated is shown outside the labelled figure on the Methods page.
- Berkeleytime-derived numbers carry "from Berkeleytime's public history" on every page that shows them (`BWO.sourceHtml`, `BWO.sourceLabel`). Whether a `meta.json` (or `backtest.json`) is Berkeleytime's is one helper every page calls, `BWO.isBerkeleytime` (`data_source` is `berkeleytime_history`); `tests/test_site.py` pins every string it decides, byte for byte, for today's meta, an own-data publish and a Berkeleytime meta without the pre-registration fields, and for the first two next to an own-data backtest.
- Horizons count down to the **forecast term** in `meta.json` (`forecast_term_name`, `deadline`, `instruction_start`, `dates`), so a finished cycle's curves can stand in for Spring 2027 (Fall 2026 until 2026-09-24, Spring 2026 since); the data term is named in the source sentence.
- "Today" is the reader's own calendar date at local midnight in the browser's time zone (`BWO.today`), or `?today=YYYY-MM-DD`, which is that date in any zone (tests pin it; a reader can ask what a page would have said). A date from the data is that calendar day at local midnight (`BWO.dateOf`), every date prints in local time (`BWO.fmtDay`, `BWO.fmtShort`, no `timeZone: "UTC"`), and horizons are whole days between dates (`BWO.horizons`: to the end of the last automatic run's day, 27 on Jan 10 for Feb 5, and to the first day of instruction; the key dates count to the date itself; `BWO.addDays` steps the calendar, so "7 days from now" survives a DST change). Before the site audit of 2026-10-27 (item 4) the pages measured from the instant to 00:00 UTC and printed in UTC, so from about 17:00 Pacific every date was tomorrow's. Internal links keep a pinned date (`BWO.withToday`).
- States every data page distinguishes: loading (skeleton), fetch failed (says so, offers reload; `state: "failed"` from `BWO.load`), no estimates yet (`meta.json` missing, `events` under 10, or no `deadline`/`instruction_start`: "No estimates yet", that the curves appear once this project's own Spring 2027 snapshots have seen enough waitlists clear (no date, so it holds before and after Phase 1 opens), and the counts so far; forms hidden), ready.
- Live data status (B2): once a page has set its status line (the source sentence on Lookup, Courses, Course and Insights, the backtest line on Accuracy, "Data status" on About and Methods), `BWO.liveStatus` reads `https://raw.githubusercontent.com/oliver139-chinesemole/berkeley-waitlist-odds/data/status.json` (written by `scraper/fetch.py` after every snapshot) with `cache: "default"`, never awaited, so it holds up neither first paint nor the data loads. It reads `last_run_at`, `n_observed`, `n_missing` and `term_id` and appends one sentence: "This project's last Fall 2026 snapshot ran about 12 min ago: 1,425 sections read, 1 not reached." (thousands separators, "1 section" singular, "about N hours ago" past 90 minutes; the term is named from Berkeley's term id, 2 + two-digit year + 2 Spring, 5 Summer or 8 Fall, and left out when the id does not fit that pattern, so the line is not read as the Spring 2027 collection the source sentence dates to Phase 1). The age is measured against the browser's clock, not `?today=`, and is never given in seconds because the CDN caches the file for about five minutes. Any failure (network, non-200, unparseable JSON, a missing or unparseable `last_run_at`, missing counts) leaves the page exactly as it was. The file is fetched once per page load (`BWO.loadStatus`, which resolves to the file and the moment it arrived, or to null, and never rejects), and the course page's board reads the same copy, so the two ages on that page agree (audit item 8, Course below); `BWO.agoText` is the one way either says an age. The line is a freshness signal only: no number from it ever enters `CLAIMS.md`. When the file's `term_id` is `meta.forecast_term_id` (`BWO.isForecastTerm`), the same call turns "begins with Phase 1 on Oct 26, 2026" into "has started" in the source sentence ("Live Spring 2027 collection by this project …") and in the Methods page's Data section ("Collection for Spring 2027 …", `#collection`, passed as `liveStatus`'s second element), so no date stands next to a Spring 2027 snapshot; before the scraper's switch, or when the file is not read, the dated form stays, and it is worded to remain true after Oct 26 (`tests/test_site_live.py`, with a 2268 and a 2272 file). Before the switch the sentence itself says so (`BWO.liveStatusText(s, now, meta)`): when the file's `term_id` is a Berkeley term id earlier than `meta.forecast_term_id` (the ids sort in time order), it reads "This project has not started collecting Spring 2027 yet; its last snapshot, of Fall 2026, ran about 37 min ago: 1,425 sections read, 1 not reached." instead of a Fall 2026 snapshot standing alone under Spring 2027 dates (audit item 7); a later term, an id outside the pattern or no meta keeps the plain sentence. Tests: `tests/test_site.py` serves `tests/fixtures/status_sample.json` (a copy of the real file) through the harness when `HARNESS_STATUS_FILE` names it; the sentence appears on every page above, and without the file, or with a truncated one, the status line is unchanged.
- "Got in" in headlines; "cleared" is defined once on the Methods page and used in the analysis. Buttons say what they do.
- What an estimate is follows `meta.estimate_level` (`BWO.estimateLevel`). At `course` (the default since the cross-term backtest), a course with 30 or more cases has its own curve and the department, then all courses, is a labelled `pooled` fallback; one sentence on the rule (`BWO.levelNote`) links the Accuracy page. At `dept`: a course's estimate is its department's curve for the bucket, the course's own cases appear as counts ("this course alone: N joiners in S sections", the "This course" column on the course page, the Cases column on Courses), nothing at department level is called pooled (the `pooled` tag and the "Too little data to call" rule apply only to all-course or level pools), the Courses filter hides only all-course pools, the Insights most-and-least list is dropped, and every page prints one sentence on the rule (`BWO.levelNote`) linking the Accuracy page.
- Colour: Berkeley Blue `#003262` and California Gold `#FDB515`. Gold has one meaning: you (your bucket, the two calendar dates, the current nav item). Blue is data. Position buckets are an ordinal ramp (`--s1` to `--s4`, validated for light and dark). No red or green verdicts. System font stack; `tabular-nums` on numbers in tables and axes only. Light and dark follow the system setting; `prefers-reduced-motion` is honoured.
- Accessibility: skip link, one `<nav aria-label="Site">` with `aria-current="page"`, ARIA combobox for search, `aria-sort` on sortable headers, `aria-live` on status and result regions, visible focus, `role="img"` with a label on every chart plus a keyboard-reachable readout and a "Show as table" twin, scroll regions focusable, 44 px targets, single column below 30 rem, no horizontal page scroll at 390 px, and every nav link whole on screen: below 30 rem the five links share the row a little tighter (15 px, one row down to 360 px) and wrap onto a second line rather than scroll out of sight (audit item 15: at 390 px "Methods" was cut to "M").

#### Course search (`BWO.matchCourse`)

`BWO.matchCourse(index, text)` returns `{key, row, layer, ranked, nearest, query}`; `BWO.findCourse` is its row, so every existing caller is unchanged. Two config files feed it, and both travel in `site/assets/site.js` between generated markers because the site ships only `site/`: `config/subject_names.json` (generated, one display name per subject in `index.json`, with its `_source` URL and `_fetched` date as data since JSON has no comments) and `config/course_nicknames.json` (hand-written, never regenerated: `E7`, `Data 8`, `Bio 1A`, `Haas`, `R&C`). `python scripts/subject_names.py` rewrites the first and the markers from the public Berkeley Academic Guide subject index ("Name (CODE)"); nothing is fetched from classes.berkeley.edu. `--check` verifies the committed files agree, which `tests/test_site.py` asserts. A code once written is kept (`--index` adds another term's index), so the file names every subject of both the Fall 2026 and the Spring 2026 index and holds whichever `site/data` ships. A Guide name written back to front with one comma (`Art, History of`, `Business Administration, Undergraduate`) is stored in reading order (`History of Art`, `Undergraduate Business Administration`) with the Guide's spelling kept under `aliases`, so both reach the name route; a name with two or more commas is a list and stays as written. Three subjects are not in the Guide's index (`DISSTD`, `MBN`, `QTP`). `DISSTD`, which the Spring 2026 index the site ships has, is named by hand in the generator's `MANUAL` map, "Disability Studies", from its courses' catalog titles ("Introduction to Disability Studies", "Women and Disability"; audit item 21: the department list showed the bare code), and `python scripts/subject_names.py` writes it into both generated files; `MBN` and `QTP`, in the Fall 2026 index only, are written blank and listed under `_todo`. The test asserts a name for every subject of the shipped index and for the 40 most-joined of both.

The matcher builds up to four readings of a query (as typed, with the split suffix rejoined, with the filler stripped, with both) and tries **all** of them without fuzzing before it tries any of them with fuzzing, so a filler word is stripped rather than mistaken for a misspelt subject (`dis 100` is the bare number 100, not a typo for `DS`). A match reports the most forgiving step it needed, from `BWO.LAYERS`: `exact` (the subject token, spaces and `&` squashed, is the catalog code, so `comp sci 61a` and `l&s 198` are exact too), `alias` (`SUBJECT_ALIASES`), `name` (the full subject name, `computer science 61a`), `nickname` (a hand nickname, which wins over everything else), `filler` (a filler token was dropped: `BERKELEY`, `UC`, `CLASS`, `COURSE`, `LEC`, `LECTURE`, `DIS`, `DISCUSSION`, `LAB`, `SPRING`, `FALL`, `SUMMER` or a four-digit year), `split` (a lone trailing letter rejoined its number, `cs 61 a`), `bare` (no subject at all, `61a`: the courses with that number ranked by `joins`, the first one looked up), `fuzzy` (a typo in the subject was forgiven), `title` (a course title or an instructor, below) and `miss`. Fuzzy is Damerau-Levenshtein on the subject token only, at most 1 for tokens of five characters or fewer and at most 2 above, over the catalog codes, the aliases and the full names, ties by the subject's `joins`; **numbers are never fuzzed**, so a fuzzy subject only counts when it names a course that exists with the number asked for, and a typo in the number is a miss. Every fuzzy hit prints "Showing COMPSCI 61A for *compsi 61a*" right under the lookup's status line, in its own element (`#showing`, `BWO.showingHtml`): a lookup (the form, a chip, a `?course=` link) never rewrites the status line, so the live status sentence and the "has started" swap survive it (`tests/test_site_live.py`). The course page prints the same line in its status area when its `?c=` needed a fuzzy, name or nickname match (`course.html?c=compsi 61a`), since a link can carry any spelling; an exact code or an alias prints nothing. The **title layer** comes last, after every code route and the fuzzy pass, and only for a title-shaped query: no digit anywhere (a query with a number is a code, and numbers are never fuzzed), at least three characters, not all filler, not only stop words (`the`, `and`, `of`, `to`, `in`, `a`, `an`, `for`, `with`, `on`, which title matching ignores: `the data structures` is `data structures`, and `and` alone is a miss although hundreds of catalog titles contain it), and not a subject on its own (`data`, `cs`, `the data`, `computer science` stay misses with their subject's courses offered). Titles and instructors live in `data/titles.json` (`{generated_at, source, catalog_term_id, courses: {key: {title, instructors}}}`, written by the analysis side; `meta.titles_file` names it), which is **loaded lazily**: fetched on the first title-shaped miss and never again in that page load, so a code query never requests it; with no `meta.titles_file`, a missing file or a failed fetch the layer is skipped silently and the query is an ordinary miss. Matching is on **whole tokens**, normalised the way a query is: every query word is a word of the title (`data structures`, `linear algebra` for "Linear Algebra and Differential Equations"; `intro` is not `Introduction`, `structure` is not `Structures`), or every query word is a word of one instructor's name and one of them is the surname (`hilfinger`, `paul hilfinger`; a first name alone matches nothing). The query is tried as typed, then with filler stripped (`berkeley data structures`). Title hits come before instructor hits, each most-joined first, and only courses in `index.json` count. Because the file arrives asynchronously the matcher has two entry points: `BWO.matchCourse` stays synchronous and never looks at titles (the combobox's `searchCourses` calls it on every keystroke, so suggestions never fetch), and `BWO.matchCourseAsync(index, text, meta)` runs it and falls through to the title layer on a miss; the lookup form and the course page's `?c=` use the async one, so a title query works end to end, and both print "Showing COMPSCI 61B for *data structures*" for a title hit as they do for a fuzzy one. A miss carries up to three `nearest` courses, only ones close to the query: the subject's own courses when the subject was understood (`cs 61x`, `math 9999`), nearest catalog number first (the numeric part, then the letter suffix nearest the one typed, then joins: `ECON 121` offers ECON 119 and its neighbours, not ECON 1; review of 2026-10-29, 3.3), else what the combobox suggests for the text (`BWO.searchCourses`: a prefix of a subject or of a key, `comp 61` offers COMPSCI 61A, 61B and 61C, and a subject alone, `data`, its courses), else the courses of the subjects within the fuzzy rule's distance of the subject token (`compsi 999`); otherwise none, and the lookup prints its no-match message without a "Did you mean" (`nope 1`, `asdf`, `data structures 2`, an empty query). Before the site audit of 2026-10-27 (item 13) the last resort was the three most-joined courses, the same three the Try chips show, offered for every query nothing resembled.

`tests/fixtures/course_queries.csv` (`query,expected_key,expected_layer`, 190 rows and 29 misses) is the fixture. It holds every row of the plan's table but one: `molecular and cell biology 32` is asked as `molecular and cell biology 104`, because MCELLBI 32 has no course in the Spring 2026 index, and `REQUIRED_QUERIES` in `tests/test_site.py` says so. It is run in two places over one matcher so the two cannot drift: `node tests/site/queries.mjs` evaluates every query inside a rendered `index.html` through `tests/site/harness.js` and exits non-zero on a failure, and `tests/test_site.py` runs that same runner and asserts every row itself. The runner sends every query through `BWO.matchCourseAsync` with `tests/fixtures/titles_sample.json` served as `data/titles.json` (the harness's `HARNESS_TITLES_FILE`, which also has `meta.json` name it), since the committed `site/data` has no titles file yet, and fails if the whole fixture requests it more than once; `tests/test_site.py` also counts the harness's fetches to pin that a code query, a digit, a bare subject, stop words alone and the combobox never request it. It is the one test that runs against the committed `site/data` rather than a synthetic export, so a row whose key is decided by the `joins` ranking (a bare number other than `61a`, `dis 100`) writes `*` for `expected_key`: the runner then accepts any course and asserts only the layer, and a new term's ranking cannot break it the way `16a` broke on Spring 2026; the ranking itself is pinned to a hand-made index in `test_a_bare_number_ranks_by_joins`. A miss offers at most three courses, computed only when something reads `nearest`, so the combobox's per-keystroke lookups do not pay for it.

### Courses (`courses.html`)

Controls in one row: position bucket (default 6-15), horizon (7, 14, 28 days; default 14), department, level, text filter (forgiving), "Hide pooled estimates" (on by default). Table: course (with level and a `pooled` tag), share who got in with its interval and "at least" before it when the reach is shorter than the horizon, nothing where it prints as 100% (`BWO.atLeastTag`, the one tag every table uses; audit item 18: it said "floor", "100% floor" included), median days, cases, sections. Any header sorts (`aria-sort`). The default order (share, highest first) is `BWO.courseDefaultOrder` (review of 2026-10-29, 2.1): rows on one section, and rows whose share is read past the curve's reach ("at least"), come after every other row, and within each group rows sort by the interval's lower bound where there is one, else by the share; a sort the reader picks, the share ascending included, is the plain order. State lives in the URL (`?bucket=&h=&dept=&level=&q=&pooled=1&sort=&dir=`). On phones (40 rem and down) the rows become two lines and, the header being hidden there, every number carries its column's name from a `data-label` ("Median days: 2.8", review of 2026-10-29, 3.1). A row opens the course page.

### Course (`course.html`)

Header, level tag, a position input that re-renders. The headline block is the same code as the lookup (`BWO.headlineHtml`); its `after` (the share, when the verdict is "Too little data to call") follows the median and cases. The no-data line for a `?c=` that is not in the index links the lookup, "which suggests courses close to what you typed when there are any" (it offers none when nothing is close, item 13). Under it, the same fallback ladder as the lookup (`BWO.ladderHtml`: the rung for the asker's bucket, then the section rung), above the source label. One chart with every bucket's curve, direct labels, legend, the asker's bucket thicker with its band, gold date markers. A table per bucket: share at 7, 14 and 28 days ("at least" past the reach, as on Courses), median, cases, got in, sections, pooled flag. Five related courses of the same subject at the same bucket: the most-joined of the subject's other courses with their own or the department's curve there (`BWO.relatedCourses`; a course on the all-course pool would only repeat that pool's number), under a sentence that says how many there are, "The 5 most-joined of the 19 other COMPSCI courses with their own or the department's curve at these positions.", or "Every other COMPSCI course with its own or the department's curve at these positions, most-joined first." when all of them fit (audit item 20). "Sections now": the live counts from `live/latest.json` on the data branch (own snapshots only; the block stays hidden when the file is absent, has no rows for the course, or holds another term than `meta.forecast_term_id`, as the Fall 2026 file does until the scraper switches to Spring 2027; `BWO.isForecastTerm`). Its first sentence gives one age with the status line (audit item 8): the board is drawn at once with its newest row's age ("as of about 3 min ago"), and when `status.json` (the same copy the status line read) names a run of the board's term, with its sentence shown, at or after that row, it is redrawn with the status line's age to the minute, since a row is rewritten only when its counts change and so can be older than the snapshot that last read it; each row keeps its own "read N min ago". A status file that fails, is for another term or is older leaves the board's own age.

### Insights (`insights.html`)

"In short": sentences composed from `insights.all_by_bucket` and `by_level` (share within 14 days by bucket, medians by bucket, lower against upper division, the counts behind them). Hero chart: lower-division courses, Phase 1 joiners, one curve per bucket (the README hero plot's data). Grid: bucket by 7, 14, 28 days and the longest follow-up, with intervals ("at least" past the reach, as on Courses; the departments' table twin too). All-course curves. Departments: dot with interval for the share within 28 days at positions 6 to 15, departments with 30 or more cases in two or more sections, with a table. When flows were exported: admits per day against the data term's calendar with Berkeleytime's dark days hatched, and how waitlisters left the queue (admitted, dropped, still waiting). Extremes: mid-list courses that moved most and least, own estimate from three or more sections, intervals shown, noise noted.

### Accuracy (`accuracy.html`)

Reads `data/backtest.json` (`analysis/export_backtest.py` from `reports/backtest_<term>/`). Without it: says the backtest is not published yet. With it, per run (split and horizon): the counts, "when the estimate said about 70%, X% got in" from the deciles of the predictor the pages use (the department curve at the department level, else the course curve, else the fixed-lead-time number), a calibration plot for it (predicted against observed by decile, with a table), the score table for every predictor in a fixed order (bucket, department, course, site v1, Cox; Brier, AUC, gain over the bucket baseline with its interval, joiners scored), and which joiners could be scored by phase. Static text lists what Fall 2026 could not test. The sentence tying the backtest to the curves shown ("The runs headed "Fit on <meta term>, scored on <backtest term>" score the curves the pages show") appears only when `meta.data_source` is `berkeleytime_history` and the two term ids differ: own-data curves were never fit on one term and scored on another, so after an own-data publish no such run exists, and the line says instead "The pages show <term> curves from this project's own snapshots; these runs test the same method on <backtest term>, not those curves." The pre-registration box prints `meta.prereg_commit` and `meta.prereg_date` when set (they describe the cohort behind the curves shown) and states what will be scored after Feb 10, 2027. When meta has neither, as after a deliberate own-data publish (the weekly run carries them only from a meta of the same term and source, PR #46), or before any meta exists, the box states the test from `BWO.PREREG` in `site.js` instead: the Spring 2026 cohort from Berkeleytime's public history, frozen at commit 7f348ed on 2026-09-21, scored after 2027-02-10, and, when `meta.data_source` is not `berkeleytime_history`, "the curves this site shows now (<`BWO.sourceLabel`>) are not part of the test". A Berkeleytime meta that lost its fields (`make site-data SITE_TERM=2268` carries nothing across terms) may be Fall 2026, itself frozen for the test at a7240f4, so it gets the record without that clause. The About page's data status does the same in one sentence. Writing that record into the script is consistent with "the site never computes a statistic": it is a fixed fact about a commit and its dates, of the same kind as the dates already written into the copy (Oct 26, 2026 in `COLLECTION_DATED`), with no number derived from data in it, and it changes only if the pre-registration does, by hand together with CLAIMS.md and docs/DATA_LOG.md. Fall 2026's frozen cohort (a7240f4) is not named on the page.

### Department (`dept.html?subject=CODE`)

The page a search result or a subreddit sidebar links for a department. Reads `meta.json`, `index.json` and `pooled.json`; no subject file, so it is one fetch lighter than the course page. `?subject=` is forgiving (`BWO.resolveSubject`: case, spaces and the subject aliases, so `cs` and `comp sci` open COMPSCI); `?bucket=` picks the starting position bucket (default 6-15, the Courses default). The page rewrites nothing in the URL; the bucket select re-renders in place. Not in the nav bar: it is reached from the course page ("All COMPSCI courses" under the related-courses heading, carrying the bucket; shown on its own when the course has no related courses) and from links. The Courses page's department filter has no link to it yet (its count line is plain text, so a link there is more than a one-line change).

- Shell: the Courses page's head, header, nav (no `aria-current`), footer and script order; `og:title` and `og:description` are static ("Department · Berkeley Waitlist Odds"), since crawlers do not run the script. `#status` is `BWO.sourceHtml(meta)` plus `BWO.levelNote(meta)`, then `BWO.liveStatus(#status)` when that function exists (the C2 branch); the footer stamp as everywhere.
- Name: `<h1>` is `BWO.subjectName(code)`, which returns `BWO.SUBJECT_NAMES[code]` once the generated map (PR #17) is on the branch and the code otherwise; when the two differ, the code shows in the breadcrumb. `document.title` is "<name> courses · Berkeley Waitlist Odds".
- A known subject: "N courses with estimates in <`BWO.sourceLabel`>", and for a subject grouped into `OTHER` one sentence saying it shares the smaller departments' curve. Then the department's pool for the bucket, `pooled.dept[dept_group][bucket]`: the share within 7, 14 and 28 days (`index.horizons`) read off the curve with `BWO.readCurve`, with intervals and "at least" past the reach, the step chart (`BWO.curveChart`, one series in the bucket's ramp colour, with its band; no date marks and no calendar dates, since the page has no "you" and no "now", so no gold), and the pool's sections, joiners and clearings. Then every course of the subject from `index.json` (`BWO.deptCourses`: most-joined first, then by number), with the Courses table's classes (two lines on phones): course (link to `course.html?c=KEY&position=<the bucket's lowest>`, level and `pooled` tag under it, as on Courses), share within 14 days at the bucket (`s.p[1]`, the field Courses shows) with its interval and "at least" past the reach, and one "Own cases" cell ("12 cases in 1 section", the course's own counts as on Courses; one cell so that the phone's second line is labelled), or "no estimate here" when the course has no cell at the bucket.
- A known subject whose department pool has no cell at the bucket (fewer than `min_n` joiners there): says so and names the buckets with a curve; the course table still shows.
- An unknown subject: "No such department", up to three close subjects as links (`BWO.nearestSubjects`, review of 2026-10-29, 3.4: subjects the text is a shorthand for or the start of, by code or by name, most-joined first, then subjects within the matcher's edit distance, `BWO.damerau` at most 2, closest first, ties alphabetical; none when nothing is that close, so `?subject=NOPE` prints only "Or browse every course."; before it every subject was ranked by plain Levenshtein distance and the nearest three printed however far), a link to Courses, no chart and no table. With no `?subject=` at all: "Departments" and every subject in the index as links.
- Loading, empty ("No estimates yet") and fetch-failed states as on every data page.
- The `BWO` additions (`subjectName`, `resolveSubject`, `nearestSubjects`, `deptCourses`) sit in one block at the end of `site.js`. Tests: `tests/test_site.py` renders the page on the synthetic export (order by joins, the pool read at three horizons, a subject without a display name and one grouped into `OTHER`, the unknown and missing subject, the nearest three for six misspellings pinned on a hand-made index, the shell, empty and failed states, the course page's link); `tests/site/smoke.mjs` opens `dept.html?subject=COMPSCI`.

## Charts (`BWO.curveChart`)

Step-drawn curves (the maths is a step function, so is the drawing), 2 px lines, band at 12% for the series that asks for one, hairline solid grid, y from 0 to 100%, x in days since joining with the calendar date under each tick when today is known, a hatched region beyond the data's reach (its title: "Beyond 80 days, the longest the data follow anyone, the share is at least the value at 80 days"), end markers with a surface ring, direct end labels nudged apart in the order of the shares they print and, where two print the same, in bucket order (audit item 19: "16-40 100%, 1-5 100%, 6-15 100%" was the order of unprinted decimals), every other x tick (its day and date, class `odd`) hidden below 30 rem so a phone gets half the labels (audit item 16; `tests/site/smoke.mjs` checks it at 390 px), gold vertical markers for the two calendar dates with staggered labels, a crosshair readout on hover, tap and arrow keys (the SVG is focusable), a legend for two or more series, and a "Show as table" details block. No animation.

## Title and instructor search: `titles.json`

`site/data/titles.json` (docs/DESIGN_A5.md section 4; `make site-data` with a data-branch checkout, or `python -m analysis.export --titles-only`) maps each course in `index.json` to its catalog `title` and `instructors`, so "data structures" or "hilfinger" can find a course (MASTER_PLAN Q4). From the Fall 2026 catalog of 2026-09-24 it held 1728 of the index's 2050 courses in 199535 bytes (49407 gzipped), so it is lazy-loaded: the matcher fetches it only when `meta.titles_file` names it and a query has no digit and no known subject token (a subject, or an alias from `SUBJECT_ALIASES`). A plain code query ("cs61a", "COMPSCI 61A", "data 8") never fetches it. Without `meta.titles_file`, or when the fetch fails, search quietly falls back to codes alone. Titles are labels from the catalog term (`catalog_term_id`); they carry no estimate and the pages compute nothing from them.

## Data branch: `live/latest.json`

Written by `scrape.yml` after every snapshot (`python -m scraper.live`, `continue-on-error: true`, same commit as the Parquet file): `generated_at`, `term_id`, `term_name`, `only_active`, `selection`, `n_sections`, `columns`, and one compact row per section (section id, course key, subject, catalog number, component, section number, enrolled, capacity, waitlist, waitlist capacity, reserved count, open reserved, status, observed at). The two reserved columns are nullable and sit between waitlist capacity and status, the snapshot schema's own order. The rows are every section of any course with at least one full or waitlisted section, so the board can answer "which section has room"; `selection` names that rule (`courses_with_a_full_or_waitlisted_section`, or `all_sections` under `--all`), and `only_active` stays for readers that exist but is false either way now, since open sections are written too. Cross-listed sections are separate rows with their own counts, never merged; a course page shows only the rows carrying its own key, and no file names a section's cross-listed partner. The site reads it from `raw.githubusercontent.com` (CORS allowed, five-minute cache); own snapshots only.
