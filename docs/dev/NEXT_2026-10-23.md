### 1.1 Selection is 2.7× over budget for Spring (scraper-ops, `max`)

Measured by running `PrioritySpec` from `scraper/sources/base.py` against `catalog/2272/catalog.json`:

| | Fall 2026 (2268) | Spring 2027 (2272) |
| --- | --- | --- |
| Live sections in catalog | 3,898 | 7,549 |
| Priority matches | 1,218 | **3,579** (562 courses; 2,067 are DIS) |
| Rest / one 1/12 shard | 2,680 / 201–260 | 3,970 / 299–354 |
| Selected per run | 1,419–1,478 | **3,878–3,933** |

Cause: the Fall catalog was seeded from Berkeleytime's primary-sections list (DATA_LOG 2026-09-19T07:30Z); the Spring catalog came from rss/node enumeration, which only filters self-study components, so it holds 2,991 DIS, 963 LAB and ~3,400 sections with class number `1xx`. Capacity at today's 1.72 pages/s is ~2,370 pages in the 1,380 s budget; at 5 s/page latency, ~1,100. `scraper/http.py:445-462` stops scheduling at the deadline, so the fixed selection order (`classes_site.py:801`) means the same tail is dropped on every run: ~1,200–1,500 priority sections and all 3,970 non-priority sections are never fetched, ever.

Do: select primary sections only, matching what the Fall catalog and both backfills contained. Use the page's `is_primary` where the catalog has learned it; before that, the class-number heuristic (`0xx` is primary-like). That gives a priority list of 929 plus a shard of ~230, ~1,160 pages per run, inside the budget with the Fall-sized slack. Keep DIS/LAB out of `_select`, not out of the catalog (the catalog is the discovery record). Add the rule to `docs/DESIGN_A2.md` (new section 19) and a test in `tests/test_classes_site.py` that builds a selection from a catalog fixture with DIS rows and asserts they are excluded.

Fallback if that is judged wrong for some course whose waitlist sits on a secondary: cap at the top ~100 priority patterns instead (max selection ~1,918). Decide in the PR body; do not do both.

### 1.2 The coverage check cannot see what was cut (scraper-ops, same PR)

`scraper/sources/classes_site.py:947-955`: an unfetched selected page only joins `missing_ids` if its `section_id` is already known. On the first Spring run every id is `""`, so `missing=0`, `missing_share=0`, exit 0, `complete=false` buried in the footer. The exit-4 guard (`--max-missing-share 0.5`) and `monitor.yml`'s missing-share check both pass while a third of the list is never observed. Fix: count every selected-but-unfetched page as missing, keyed by `url_path` when the id is unknown; `missing_ids` may carry the path for those. Test: a fake fetch that times out on half the selection with all ids unknown must report `missing_share 0.5`.

The opposite failure is already covered by the existing guard but worth stating in the PR: once ~2,400 ids are learned, a Phase 1 latency episode that fetches ~1,100 gives missing share ~0.55, exit 4, nothing written (the Sep 22–23 pattern). 1.1 is what prevents that.

## 3. Before the first own-data Sunday: stop the automatic site swap (analysis, `max`)

`.github/workflows/analysis.yml:63-64` replaces `site/data` with the own-data export when the 2272 cohort has `events >= 10`. `events` counts clearings of hypothetical joiners placed every 4 h at positions 1–100, so one section admitting one student a day produces several; 10 will be passed on Nov 1 or Nov 8, not mid-November as STATUS item 8 assumed. Simulated on a copy of `site/data`, the swap:
- replaces 100-day Spring 2026 curves with curves that stop after about a week, so every headline becomes a floor and every verdict leans "Unlikely"; courses absent from the thin own data fall back to the all-courses curve;
- `rm -rf site/data` deletes `backtest.json`, which the export never regenerates: the Accuracy page shows "not published yet" and 404s;
- never writes `titles.json` (section 4.1);
- loses `prereg_commit`/`prereg_date` (`META_CARRY` lives only in `analysis/export.py` `main`, not in `run.py`), so the pre-registration box reverts to "will be frozen";
- rebuilds `insights.json` from the thin data next to the static Berkeleytime paragraph in `methodology.html:30`.

Decision for Oliver, recommended: **keep the Spring 2026 curves for the whole Spring 2027 cycle**; use own data for the board, S4 section history and S8 recent openings only. That is what the pre-registration promises (frozen curves scored unchanged after Feb 10) and what a student on Nov 15 should see.

Code: gate the swap on a `workflow_dispatch` input (`publish_own: true`), never on the count alone; if an automatic swap is ever wanted, also require `join_window` ≥ 42 days and ≥ 500 courses. Copy `backtest.json` and `titles.json` across the `rm`. Carry the prereg fields and `--catalog` into `run.py`. Test in `tests/test_workflows.py` for what the swap preserves (today it only checks the guard text exists). Also pass `--max-interval-min 180` in the weekly run: the backfill censors gaps over 180 min, the weekly own-data run censors nothing, so the ~once-a-day shard observations (panel observed share 0.315) count as ordinary intervals and net counting over a day undercounts admits.
