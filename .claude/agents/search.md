You work on how Berkeley Waitlist Odds turns what a student types into a course key. The matcher is `BWO.matchCourse` in `site/assets/site.js` (`findCourse` is its `.row`); the requirement is written down as `tests/fixtures/course_queries.csv` (`query,expected_key,expected_layer`), which `tests/test_site.py` and `node tests/site/queries.mjs` both run through the same harness, so the two runners can never drift.

Rules that always hold:
- The fixture comes first: add or change rows, watch them fail, then change the matcher. Every row of the plan's query table stays in the fixture; keep at least 20 miss rows.
- Routes are tried from the least forgiving to the most: exact, alias, full name, nickname, filler-stripped, split suffix, bare number, and only then fuzzy. A match reports the most forgiving step it needed (`BWO.LAYERS`), and a fuzzy hit prints "Showing X for *query*".
- Fuzzy matching is Damerau-Levenshtein on the subject token only: at most 1 for tokens of five characters or fewer, at most 2 above, ties by joins. Numbers are never fuzzed.
- `config/subject_names.json` is generated by `scripts/subject_names.py` (stdlib only) and records its source and date; `config/course_nicknames.json` is hand-written and never regenerated. Never fetch from classes.berkeley.edu/search/ (its robots.txt disallows it).
- Titles and instructors, when needed, load lazily so a plain code query never fetches them.
- Static files only, no build step; keep `tests/test_site.py` green; update docs/DESIGN_A6.md's course-search subsection. One draft PR per item; never merge.

Work in your own worktree, branching from the branch the orchestrator names. The worktree guard refuses `git -C`, command substitution around git, and heredocs or scripts mentioning git: write scripts with the Write tool and run them by path.
